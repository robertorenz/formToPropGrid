OverviewResumen

One object is one property grid. You give it a window and a rectangle, add categories and rows, and pump its events from a timer. PROPGRID.DLL does the drawing with Direct2D and DirectWrite; PropGridClass does everything the DLL cannot know about — reading the Clarion window, writing back into USE variables, folding lookup trios and handling tabs.

Object modelModelo del objeto

What it owns, what it only borrows

The class owns a handle and three private registries; it borrows the window and its controls for the duration of one call and hands them back.

OwnsBorrows
  • The HPG handle in PG — 0 means dead
  • Lookups, Tabs, CatNames — three NEWed queues, all PRIVATE
  • Every setting: Style, LiveSync, HideOriginals, DockMode, MaxScanItems
  • The pending-refresh counter PendingSyncFrom
  • The window, held by reference in Win
  • The placeholder REGION's rectangle, read on every Reposition
  • The controls' USE variables — read with CONTENTS, written with CHANGE
  • The controls' visibility: it hides originals and can hide emptied TABs

One object, one grid

The control template is MULTI, so a window may carry several independent grids. Every generated label carries %ActiveTemplateInstance, and each instance gets its own object, its own category ids and its own private resize event — nothing is shared.

The tag is the contract. SetTag(row, feq) is what binds a row to a control. A row with no tag — an "added" row bound to a variable rather than a control — is silently skipped by SyncBack, SyncRow and SyncFrom. That is by design: it is what lets the template mix control-bound and variable-bound rows in one grid.

Qué posee y qué sólo toma prestado

La clase posee un handle y tres registros privados; toma prestada la ventana y sus controles mientras dura una llamada, y los devuelve.

PoseeToma prestado
  • El handle HPG en PG — 0 significa muerto
  • Lookups, Tabs, CatNames — tres colas creadas con NEW, todas PRIVATE
  • Cada ajuste: Style, LiveSync, HideOriginals, DockMode, MaxScanItems
  • El contador de refresco pendiente PendingSyncFrom
  • La ventana, guardada por referencia en Win
  • El rectángulo del REGION marcador, leído en cada Reposition
  • Las variables USE de los controles — leídas con CONTENTS, escritas con CHANGE
  • La visibilidad de los controles: oculta los originales y puede ocultar las TAB que quedaron vacías

Un objeto, una rejilla

La plantilla de control es MULTI, así que una ventana puede llevar varias rejillas independientes. Cada etiqueta generada lleva %ActiveTemplateInstance, y cada instancia tiene su objeto, sus ids de categoría y su evento privado de redimensión — no se comparte nada.

El tag es el contrato. SetTag(row, feq) es lo que une una fila con un control. Una fila sin tag — una fila "agregada", ligada a una variable y no a un control — es ignorada en silencio por SyncBack, SyncRow y SyncFrom. Es a propósito: es lo que permite mezclar filas ligadas a controles y a variables en una sola rejilla.

Multi-DLL

Where the class's code lives is decided by two project defines, _PropGridLinkMode_ and _PropGridDllMode_, which the templates generate through the ABC class category PROPGRID. With neither define present — a hand-coded project — LINK behaves as 1 and DLL as 0, which is exactly single-EXE behaviour.

Never EQUATE the two modes by hand. They must arrive as project defines. With no values at all the DLL() attribute is undefined and every virtual call dies with an access violation — which is why PropGrid.inc carries a guarded default block that must never be removed. In a multi-DLL suite the PropGridGlobal extension has to be on every app, or that app quietly compiles a private copy of the class.

Life cycle & orderCiclo de vida y orden

The order is the whole design. Several methods only record something that a later method acts on, so calling them late is the same as not calling them at all.

#CallWhy here

3SetFont, SetColor, SetRowHeight, SetSplitterAny time after Init, but doing it now avoids a visible repaint.

Set TimerInterval = 0 to leave the window completely alone — then pumping is your job.

PropGridLookupQueue

The classic Clarion lookup is three controls: an ENTRY holding the code, a '...' BUTTON that opens a select browse, and a STRING showing the description. AddFileDrop folds all three into one drop-down row that shows the description and writes the code back. This queue is the registry of those folds — one entry per trio.

! PropGrid.inc:87
PropGridLookupQueue QUEUE,TYPE
Row                   SIGNED       ! grid row id (also the SetTag row)
CodeFeq               SIGNED       ! control holding the code   (hidden)
NameFeq               SIGNED       ! control showing the name   (hidden, 0 = none)
Codes                 STRING(2048) ! 'A|B|C'       - written back
Names                 STRING(4096) ! 'Ape|Bee|Cat' - displayed
                    END
FieldMeaning and invariants
RowThe row returned by AddProperty. It is also the row that carries SetTag(row, codeFeq) — without that tag, no sync method would ever look at this row.
CodeFeqThe real ENTRY. Hidden by AddFileDrop unconditionally — the drop row has replaced it — and the destination of every write-back.
NameFeqThe description control, or 0. Hidden and kept in step, so a form that saves it to the file still saves the right text.
CodesPipe list of the values written back. Item n pairs with item n of Names.
NamesPipe list the grid shows, and the row's SetChoices string. Twice the capacity, because descriptions are longer than codes.

The parallel-list invariant

Everything about this queue rests on one rule: item n of Codes is the code for item n of Names. Build both lists in the same loop, and push every value through PipeSafe so a | inside the data cannot split the list.

Matching is done by PipeFind, which is case-insensitive, blank-tolerant and — when both sides are numeric — value-tolerant, so '1' finds '001' and '1.00' finds '1'. An exact text match always wins over a numeric one. A code that is in the control but not in the list is shown raw rather than blanked.

The round trip

! grid -> control : the user picked a description, write the code   (clw:695)
PropGridClass.SyncRow PROCEDURE(SIGNED row)
  CODE
  feq = SELF.GetTag(row)

    END

    RETURN
  END

FindLookup fixes the buffer. FindLookup(row) returns 1 and leaves SELF.Lookups sitting on the matching entry; every caller reads SELF.Lookups.CodeFeq straight afterwards. If you override SyncRow, do not call anything that moves that queue between the FindLookup and your reads.
It suits code tables, not big files. The file is read once, when the window opens. MaxScanItems (500) caps the scan, and the templates stop at 1900 / 3900 characters to stay inside the two STRINGs — a big table is truncated silently. For anything large, leave the browse button alone.

La búsqueda clásica de Clarion son tres controles: un ENTRY con el código, un BOTÓN '...' que abre un browse de selección, y un STRING que muestra la descripción. AddFileDrop pliega los tres en una sola fila desplegable que muestra la descripción y escribe el código de vuelta. Esta cola es el registro de esos pliegues — una entrada por trío.

CampoSignificado e invariantes
RowLa fila que devolvió AddProperty. Es también la que lleva SetTag(row, codeFeq) — sin ese tag ningún método de sincronización miraría esta fila.
CodeFeqEl ENTRY real. AddFileDrop lo oculta siempre — la fila desplegable lo reemplazó — y es el destino de toda escritura.
NameFeqEl control de descripción, o 0. Se oculta y se mantiene al día, para que un formulario que lo guarde en el archivo guarde el texto correcto.

La invariante de las listas paralelas

Todo en esta cola descansa en una regla: el elemento n de Codes es el código del elemento n de Names. Construya las dos listas en el mismo bucle y pase cada valor por PipeSafe, para que un | dentro de los datos no parta la lista.

La búsqueda la hace PipeFind, que ignora mayúsculas y espacios y — cuando ambos lados son numéricos — también el formato, de modo que '1' encuentra '001' y '1.00' encuentra '1'. Una coincidencia exacta de texto siempre gana. Un código que está en el control pero no en la lista se muestra tal cual, no en blanco.

PropGridClass.TabCategory PROCEDURE(SIGNED tabFeq, SIGNED fallback)

TabCategoryOf(feq) is the public entry point: it walks PROP:Parent up from any control to the nearest TAB and returns that tab's category, creating it on demand. 0 means the control is not inside a TAB — use your default category instead.

PGFTCat = FormGrid.TabCategoryOf(?CUS:DeptCode)  ! the tab this lookup sits on
IF ~PGFTCat THEN PGFTCat = PGFCat.            ! not on a tab - default category
Ordering, both ends. SetTabCategory only records the override, so it must run before BuildFromWindow. TrimTabs is the mirror image: it must run after every AddFileDrop and after any hand-hiding, because a tab that is nothing but lookups only empties once the trios are folded.
What survives a Kill. Kill and ClearAll zero every CatId — the headers died with the rows — but keep TabFeq and CatName. Re-initialising on the same window therefore keeps the tab naming you configured, without re-registering anything.

BuildFromWindow, step by stepBuildFromWindow, paso a paso

One loop, FIRSTFIELD() to LASTFIELD(), with SETTARGET(SELF.Win) held for the whole walk and dropped around each AddControl.

  1. No type? PROP:Type of 0 means there is no control at that equate — skip.
  2. Our own REGION? Skip it, or the grid would try to convert its own placeholder.
  3. Excluded? IsExcluded checks the FEQ and every container above it. On a hit the remembered label is dropped as well, so the next control cannot steal the prompt that belonged to the excluded one.
  4. Already hidden? Skip — a control the developer hid stays hidden and unconverted.
  5. PROMPT / STRING? Remember it as the label for the next data control and move on.
  6. A container or decoration? RADIO, SHEET, TAB, GROUP, PANEL, IMAGE, LINE, BOX, ELLIPSE, REGION, MENU, ITEM, MENUBAR, TOOLBAR, PROGRESS, CUSTOM, OLE — skipped.
  7. Which category? OwnerTab(feq) walks PROP:Parent up to the nearest TAB; if there is one, TabCategory supplies its category, falling back to the one you passed in.
  8. Convert. NextPrompt is set to the remembered label, target is dropped, and AddControl builds the row.
  9. Hide. With HideOriginals on, the control and its label both go.
  10. Forget the label and continue.
Why the label is a separate step. A Clarion window carries no link between a PROMPT and the control it labels — the only evidence is declaration order. That is why the walk remembers the last label seen and why anything unexpected in between throws it away rather than guessing. PrevLabelFeq clw:1039 does the same job backwards for AddFileDrop, stepping over the description control and giving up after 32 equates.

Un solo bucle, de FIRSTFIELD() a LASTFIELD(), con SETTARGET(SELF.Win) activo durante todo el recorrido y soltado alrededor de cada AddControl.

  1. ¿Sin tipo? Un PROP:Type de 0 significa que no hay control en ese equate — saltar.
  2. ¿Nuestro propio REGION? Saltarlo, o la rejilla intentaría convertir su propio marcador.
  3. ¿Excluido? IsExcluded revisa el FEQ y todos los contenedores por encima. Si acierta, la etiqueta recordada se descarta también, para que el siguiente control no le robe el prompt al excluido.
  4. ¿Ya oculto? Saltar — un control que el programador ocultó sigue oculto y sin convertir.
  5. ¿PROMPT / STRING? Recordarlo como etiqueta del siguiente control de datos y seguir.
  6. ¿Contenedor o adorno? RADIO, SHEET, TAB, GROUP, PANEL, IMAGE, LINE, BOX, ELLIPSE, REGION, MENU, ITEM, MENUBAR, TOOLBAR, PROGRESS, CUSTOM, OLE — se omiten.
  7. ¿Qué categoría? OwnerTab(feq) sube por PROP:Parent hasta la TAB más cercana; si la hay, TabCategory aporta su categoría, con la que usted pasó como respaldo.
  8. Convertir. Se pone NextPrompt con la etiqueta recordada, se suelta el target y AddControl construye la fila.
  9. Ocultar. Con HideOriginals encendido, se van el control y su etiqueta.
  10. Olvidar la etiqueta y continuar.
Por qué la etiqueta es un paso aparte. Una ventana de Clarion no lleva ningún vínculo entre un PROMPT y el control que etiqueta — la única evidencia es el orden de declaración. Folding a lookup trioPlegar un trío de búsqueda

What the template generates for one lookup, written out by hand. Note SaveBuffer / RestoreBuffer around the scan: reading the lookup file has to leave the record buffer exactly as it found it.

codes STRING(2048)
names STRING(4096)
cnt   SIGNED
buf   USHORT
row   SIGNED
  CODE
  codes = ''
  names = ''
  cnt   = 0
  Relate:Departments.Open()                    ! reference counted - safe to nest
  buf = Access:Departments.SaveBuffer()
  SET(DEP:CodeKey)
  LOOP
    IF Access:Departments.Next() THEN BREAK.
    IF cnt >= FormGrid.MaxScanItems THEN BREAK.
    IF LEN(CLIP(codes)) > 1900 THEN BREAK.     ! stay inside STRING(2048)
    IF LEN(CLIP(names)) > 3900 THEN BREAK.     ! stay inside STRING(4096)
    cnt += 1
    IF cnt = 1
      codes = FormGrid.PipeSafe(DEP:Code)
      names = FormGrid.PipeSafe(DEP:Name)
    ELSE
      codes = CLIP(codes) & '|' & FormGrid.PipeSafe(DEP:Code)
      names = CLIP(names) & '|' & FormGrid.PipeSafe(DEP:Name)
    END
  END
  Access:Departments.RestoreBuffer(buf)
  Relate:Departments.Close()

  row = FormGrid.AddFileDrop(PGFCat, 'Department',   |
          ?CUS:DeptCode,                             |  ! hidden, holds the code
          ?CUS:DeptName,                             |  ! hidden, shows the name
          CLIP(codes), CLIP(names),                  |
          'Which department owns this customer')
  HIDE(?LookupDept)                             ! the '...' button is now redundant
