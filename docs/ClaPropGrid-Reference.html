ClaPropGrid developer reference

A property grid rendered by a native Direct2D DLL, wired into AppGen by three templates. This is the reference for the wrapper class, its three internal registry queues, the design-time symbol lists that feed them, and the code the templates generate.

01Overview

Three files carry the whole system. propgrid.dll renders the grid with Direct2D/DirectWrite and exposes a flat __stdcall C API. PropGridClass (PropGrid.inc / PropGrid.clw) wraps that API in ABC-flavoured Clarion and adds everything the DLL cannot know about: window reflection, USE-variable write-back, lookup folding and tab handling. ClaPropGrid.tpl / .tpw drive the class from AppGen.

The class keeps three private QUEUEs — a lookup registry, a tab registry and a category-name registry. They are the reason a converted form behaves like one coherent grid instead of a pile of rows, and they are what most of this document is about.

PropGridLookupQueueOne entry per folded lookup trio. Maps a grid row to the hidden code control and its parallel code/name lists.
PropGridTabQueueOne entry per TAB that fed a row. Holds the category-name override and the lazily created category id.
PropGridCatQueueName → id. Makes AddCategory merge by name, so four row sources land under one header.

02Architecture

Work happens in three separate times, and confusing them is the usual source of template bugs. Parse time is AppGen showing prompts and running #GROUP scans over the window. Generate time is the #AT blocks emitting Clarion source into embed points. Run time is the generated source driving PropGridClass, which drives the DLL.

Why the priorities are what they are

ABC opens the window at 8000, restores its saved size at 8250 and runs the field templates at 8500 — so the grid is created at 8600, when the REGION has its final size and PROP:Handle is live. The event pump sits at 2000 in TakeWindowEvent, above the framework's own LOOP/CASE scaffolding at 2500; using 2500 interleaves and emits a duplicate CASE EVENT(). Kill runs at 7500, above ABC's "already killed" short-stop at 5100.

PropGridLookupQueue

The classic Clarion lookup is three controls: an ENTRY holding the code, a '...' BUTTON that opens a select browse, and a STRING showing the description. AddFileDrop folds all three into one PGT:Drop row that displays the description and writes the code back — no browse involved.

FieldMeaning & invariants
Identity
RowThe grid row returned by AddProperty. Also the row's tag target: SetTag(row, codeFeq) is what lets SyncRow find the control at all.
CodeFeqThe real ENTRY. Hidden by AddFileDrop unconditionally — the drop row has replaced it — and the destination of every write-back.
NameFeqThe description control, or 0. Hidden and kept in step, so a form that saves it to the file still saves the right text.
Parallel lists
CodesPipe list of the values written back. Item n pairs with item n of Names. Build with PipeSafe(), which turns a | inside the data into /.
NamesPipe list the grid shows, and the row's SetChoices string. Twice the capacity of Codes because descriptions are longer.

Matching is done by PipeFind, which is case-insensitive, blank-tolerant and — when both sides are numeric — value-tolerant, so '1' finds '001'. An exact text match always beats a numeric one. An unknown code is shown raw rather than blanked.

FindLookup fixes the buffer

FindLookup(row) returns 1 and leaves SELF.Lookups sitting on the matching entry. Every caller reads SELF.Lookups.CodeFeq straight afterwards. If you override SyncRow in a derived class, do not call anything that moves that queue between the FindLookup and your reads.

PropGridTabQueue

One entry per TAB that has fed a row into the grid, or that SetTabCategory pre-registered. The category id is lazy: the header is only created when the first row actually lands under it, so a tab whose every control was excluded never leaves an empty header behind.

PathResulting category
CatId already setReturned as is — one header per tab, however many rows ask.
CatName setAn explicit SetTabCategory override always wins, even with TabCategories off.
TabCategories = 1The TAB's own text, with accelerator ampersands stripped by ControlLabel.
otherwiseThe caller's fallback — normally the default category.

TabCategoryOf(feq) is the public entry point: it walks PROP:Parent up from any control to the nearest TAB and returns that tab's category, creating it on demand. 0 means the control is not inside a TAB — use your default category. The generated form template uses exactly that idiom to put a lookup row on the tab its code control lives on.

Ordering

SetTabCategory only records the override — it must run before BuildFromWindow, or the tab's own text will already have created the header. TrimTabs is the mirror image: it must run after every AddFileDrop and after any hand-hiding, because a tab that is nothing but lookups only empties once the trios are folded.

PropGridCatQueue

The smallest of the three and the one that makes the grid feel designed rather than assembled. AddCategory merges by name: asking twice for 'General' returns the same header, whichever of the four row sources asked — the default category, a tab, a lookup row, an added row, or your own code.

Comparison is case-insensitive after CLIP/LEFT, so 'general', ' General' and 'GENERAL' are one header. This is why the templates can let you type a category name freely on a lookup, an added row and the actions block without producing three identical headers.

The hidden child

%F2PTabKind records whether a conversion-list line is a TAB or a single CONTROL. It is written by the scan and never shown, using the shipped idiom for carrying hidden state on a repeating list — a zero-sized #BOXED guarded by %False:

It defaults to TAB so that a line you add by hand still honours the Category-name prompt, which applies to tab lines only.

The two window scans

Both run at prompt time from a #BUTTON(...),WHENACCEPTED(...) with an empty body, and both live in the .tpl rather than the .tpw: a #GROUP in the included file that reads the calling template's own symbols has been measured to come back empty.

%PGScanLookupsWhat it does
pass 1Walks #FOR(%Control) in declaration order. Every ENTRY/SPIN opens a candidate trio and records %PostLookupKey / %PreLookupKey (ABC's own per-control lookup prompts) and any DROPID. A BUTTON joins the trio only if it proves itself — ABC's %ControlToLookup points at the ENTRY, the name contains LOOKUP, or the caption is exactly '...' — because the generated code HIDEs it. The next data control closes the trio.
pass 2Resolves the table and fields. #FIND(%Key,…) fixes %File too, so a configured Lookup Key gives file and code field exactly. Otherwise the description STRING's own USE field names its file, or a MANY:1 relation supplies the code field, or the primary key's first component does. The description field is a guess — check it.
appendOnly candidates that resolved to a table and a code field are added. A trio already listed is skipped, never overwritten, so re-scanning after you edit the window is safe. Unresolvable trios are counted so you know to add them by hand.
%PGScanTabsWhat it does
pass 1Collects every candidate in window order. A LIST with no DROP(rows) attribute is a browse, not a property — the shipped test, read from %ControlUnsplitStatement so a long FORMAT split over continuation lines cannot hide the attribute.
pass 2Walks %ControlParent up (bounded at 16 steps, so a cycle can never hang AppGen) to find the TAB that owns each control — a control inside a GROUP inside a TAB is still found.
pass 3Decides each tab's action. A tab already in the list keeps your choice; otherwise a tab holding a browse defaults to Leave alone and everything else converts.
pass 4Appends what is missing, in window order. Controls on a "leave alone" tab are never listed — the tab's own entry already covers them, because excluding a container excludes its whole subtree.
Template-language traps

A multi-argument %() group call from inside a #FOR over a MULTI list expands empty and silently kills the enclosing #AT — that is why the generated code uses plain #SETs where a #GROUP would read better. And a #DECLARE + #SET is invisible to the #AT embed matcher, so the OK/Cancel control names are lazy #EQUATEs instead.

Byte order

Clarion and Win32 COLORREF store colours as 0BBGGRRh, so the hex digits read blue-green-red. 005F3A1Fh is not a brown — it is RGB 1F 3A 5F, a deep steel blue. Use the template's colour picker and you never have to think about it.

07Worked examples

A. Hand-coded, no template

The class works in a plain source procedure. With neither project define present, LINK behaves as 1 and DLL as 0 — exactly single-EXE behaviour — so nothing but the include is needed.

B. Folding a lookup trio by hand

What the FormToPropertyGrid template generates for one entry in %F2PLookup, written out. Note SaveBuffer/RestoreBuffer around the scan — reading the lookup file must leave the record buffer exactly as it found it.

Scale

The file is read once, when the window opens, so this suits code tables — departments, states, statuses. The MaxScanItems cap (500) and the two length guards mean a big table is silently truncated rather than overflowing; for anything large, leave the browse button alone.

C. Deriving the class

TakeSelect is an empty hook and TakeChanged only syncs — both are the natural override points for a grid that drives something else on the window.

D. Converting a form with tabs and lookups

The order of these calls is the whole design. Exclusions are collected first because the list is an argument to BuildFromWindow; tab category overrides are recorded before it because they only take effect at build time; TrimTabs runs last because a tab full of lookups only empties once the trios are folded.

08Generated surface

Both templates put their transfer code in procedure ROUTINEs, so ThisWindow's methods can DO them — the same pattern ABC uses for its own Do DefineListboxStyle. You can DO them yourself from any embed.

RoutineTemplateDoes
PGLoad:objPropertyGridControlVariables → grid. Runs once after the grid is built; DO it again whenever the variables change behind the grid's back.
PGSave:objPropertyGridControlGrid → variables. Called from the timer when Live sync is on; otherwise call it from your OK button.
PGPlace:objFormToPropertyGridComputes the rectangle and creates the grid, or moves it on every later call. DO it after you resize anything yourself.
PGFLoad:objFormToPropertyGridVariables → the added rows only. Converted controls look after themselves.
PGFSave:objFormToPropertyGridAdded rows → variables. Runs on OK before SyncBack, and every tick when Live sync is on.

The one configuration that writes nothing back

With Live sync off, SyncBack() is generated on the OK button only. If the window has no OK button and you leave the prompt blank, nothing ever pushes the grid into the USE variables. Either turn Live sync on, or call <object>.SyncBack() from your own embed.

09Runtime facts

These were measured by probing a live Clarion 12 window, and the class is built around them. They are the answers to "why is the code doing it the long way".

FactConsequence
PROP:Text on ENTRY/SPINReturns the picture without the leading @ — 'd17', 'n-9.2'. ControlPicture() puts it back.
CONTENTS(feq)Returns the raw USE variable, never the formatted display text, so @D/@T values must be FORMATed for the grid.
CHANGE(feq, value)Converts string→numeric plainly. Feeding it a REAL loses the decimal point, so dates and times round-trip through a LONG.
OPTIONWrite with feq{PROP:Selected} = ordinal, which honours a RADIO's VALUE attribute. CHANGE() on an OPTION corrupts it.
CHECKPROP:Checked is read only. Write with CHANGE(feq, PROP:TrueValue / PROP:FalseValue), defaulting to 1/0.
PROP:FromReads back only for a string FROM(). A queue-driven DROP has to be enumerated by walking PROP:Selected 1..PROP:Items, then restoring the selection.
PROP:UseGives the USE variable's value, not its name — and a field-equate-only USE reads back blank. So "does this control have a USE variable?" cannot be asked; SetNameControl writes with CHANGE(), verifies with CONTENTS(), and only falls back to PROP:Text when they disagree.
Button rowsA grid BUTTON row POSTs EVENT:Accepted to the real control; that event — and any browse it opens — is processed while the ACCEPT loop is suspended. PendingSyncFrom therefore counts two ticks before calling SyncFrom(): one is not enough if EVENT:Timer was already queued.
EVENT:SizedAt the top of TakeWindowEvent the ABC resizer has not moved the REGION yet, so its PROP:Width is still the old size. The generated code POSTs a private event and repositions when that arrives.
SETTARGETEvery private helper assumes SETTARGET(SELF.Win) is active. Public methods set and clear it themselves; if you override one, preserve that discipline.

The number one support symptom

The registry stores a parsed copy of the template. After editing, you must re-copy the files and re-run ClarionCL -tr, with the IDE closed. That is what the version stamp is for: it appears in the registry description and on every template's General tab. If the prompt sheet shows an older stamp than the top of ClaPropGrid.tpl, you are looking at a stale parsed copy — close the IDE, re-register, reopen.

The stamp cannot be single-sourced: the #TEMPLATE description is read at registration time, long before any #GROUP can run. It is a literal in five places — the header comment, the #TEMPLATE line, and one #DISPLAY on each of the three templates — and every edit to the chain bumps all five.

Multi-DLL

Where the class's code lives is decided by _PropGridLinkMode_ / _PropGridDllMode_, generated through the ABC class category PROPGRID by the PropGridGlobal extension. With neither define present, LINK behaves as 1 and DLL as 0 — correct for a single EXE. In a multi-DLL suite the global extension must be on every app, or that app quietly compiles a private copy of the class. Never EQUATE the two modes by hand; they must arrive as project defines.
